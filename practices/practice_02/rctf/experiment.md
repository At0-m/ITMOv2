# R.C.T.F.

Файл ведёт OpenCode по вашим запросам. Агент записывает фактические результаты экспериментов и вносит изменения в связанные файлы. Свою оценку сообщайте ему в чате; вручную заполнять шаблон не нужно.

- **Role:** Технический проджект‑менеджер, планирующий поставку backend‑сервиса AI code review
- **Context:** Используются только источники Practice 1: @practices/practice_01/project_management.md, @practices/practice_01/problem.md, @practices/practice_01/analysis.md, @practices/practice_01/adr.md, @practices/practice_01/CASE.md. Файлы Practice 1 — только источники, их не изменяем. План должен соответствовать требованиям и ограничениям из CASE.md, без придумывания новых требований.
- **Task:** Предложить улучшенный план поставки AI‑помощника code review из трёх последовательных инкрементов, ориентированный на продукт, а не учебные шаги.
- **Format:**
  1. Таблица: | Инкремент | Наблюдаемый результат | Что делает человек | Что делает AI | Проверка | Зависимости |
  2. После таблицы кратко указать: какие слабые места исходного плана исправлены; почему новый вариант лучше; какие моменты всё ещё требуют решения человеком.

## Полный запрос

```
Role:
Ты технический проджект менеджер , который планирует поставку
backend-сервиса AI code review.

Context:
Используй только как источники:

@practices/practice_01/project_management.md
@practices/practice_01/problem.md
@practices/practice_01/analysis.md
@practices/practice_01/adr.md
@practices/practice_01/CASE.md

Текущий project_management.md - результат Practice 1.
В нём есть слабое место: план местами описывает учебный процесс
(например, создание P1-02), а не поставку самого продукта.

Файлы Practice 1 являются только источниками.
Не изменяй их.

Task:
Предложи улучшенный план поставки AI-помощника code review из трёх
последовательных инкрементов.

Для каждого инкремента опиши:
- наблюдаемый результат продукта;
- что делает человек;
- что делает AI;
- как проверить результат;
- зависимости.

План должен быть связан с требованиями и ограничениями из CASE.md.
Не придумывай новые требования и не выдавай предположения за факты.

Format:
1. Таблица:

| Инкремент | Наблюдаемый результат | Что делает человек | Что делает AI | Проверка | Зависимости |

2. После таблицы кратко укажи:
- какие слабые места исходного плана исправлены;
- почему новый вариант лучше;
- какие моменты всё ещё требуют решения человеком.

Не изменяй никакие файлы Practice 1.
Верни только результат эксперимента.
```

## Что получили

| Инкремент | Наблюдаемый результат | Что делает человек | Что делает AI | Проверка | Зависимости |
|---|---|---|---|---|---|
| 1. Контракт и входная безопасность (OUT-1, API-1, SEC-1, SCOPE-1) | POST /api/reviews возвращает JSON строго по OUT-1: `summary`, `risks` (≤3 элемента с `file`, `line`, `evidence`, `risk`), `checks`. Диффы > 20 000 символов получают 413 (API-1). Перед вызовом модели секреты в diff редактируются (SEC-1) с учётом разных форматов (токены, пароли, приватные ключи); признан риск ложных пропусков и предусмотрен контроль отсутствия секретов в исходящем payload. Сервис только советует, никаких внешних действий (SCOPE-1). | Готовит diff и отправляет запрос. Читает `summary/risks/checks`, при необходимости вручную запускает предложенные проверки. Решение по PR принимает сам. | Получает от сервиса уже отредактированный diff, формирует краткое резюме, выделяет до 3 рисков с привязкой к файлу и строке и список проверок. Соблюдает формат OUT-1. | - Интеграционный тест API-1: diff длиной > 20 000 → HTTP 413. - Тест SEC-1: ввод примеров разных форматов секретов → в исходящих вызовах/промпте секреты заменены на [REDACTED]; проверка отсутствия секретов в outbound payload. - Валидация JSON‑схемы OUT-1: структура ответа ровно `summary/risks/checks` и в `risks` ≤3 элементов с нужными полями. - Проверка SCOPE-1: отсутствие вызовов approve/merge/изменения кода. | CASE.md (API-1, SEC-1, OUT-1, SCOPE-1). Доступ к внешнему LLM. |
| 2. Надёжность и наблюдаемость (REL-1, OBS-1, OUT-1 стабильность) | Вызовы LLM ограничены таймаутом 10 секунд (REL-1). Ошибки и таймауты на уровне backend/LLM‑адаптера преобразуются в контролируемый OUT-1‑совместимый ответ без 500. Логи содержат только `request_id`, длительность и статус (OBS-1). | Отправляет запросы, включая сценарии с искусственной задержкой. Проверяет, что нет 500, а ответ предсказуемый и в формате OUT-1. Смотрит технические логи для подтверждения OBS-1. | AI формирует содержимое ответа, если ответ пришёл в срок; ограничение на 10 секунд и преобразование ошибок/таймаутов в контролируемый OUT-1 выполняет backend/LLM‑адаптер. | - Интеграционный тест REL-1: симулировать задержку > 10 секунд → нет 500; контролируемый OUT-1‑ответ (преобразование на уровне адаптера). - Проверка OBS-1: в логах только `request_id`, длительность, статус; отсутствует содержимое diff и ответ модели. - Повторная валидация OUT-1 схемы при ошибках. | Инкремент 1. Канал логирования/метрики. CASE.md (REL-1, OBS-1, OUT-1). |
| 3. Полезность и точность вывода (QA-1, OUT-1 усиление) | В ответ включаются только подтверждённые риски (QA-1): каждый риск содержит ссылку на файл и строку, а `evidence` — цитату из diff или ссылку на правило репозитория. Список `checks` воспроизводим. DoD: для каждого риска есть проверяемое evidence, рисков не более 3, все указанные `checks` можно выполнить вручную и получить ожидаемый результат. | Отправляет реальные диффы. Для каждого риска переходит к указанной строке в diff, вручную сверяет `evidence` и запускает предложенные проверки. Принимает решение по PR. | Извлекает и возвращает только те риски, которые можно привязать к конкретной строке diff или правилу из CASE.md, дедуплицирует до 3 штук, формирует воспроизводимые проверки. Не выполняет действий (SCOPE-1). | - E2E по QA-1: для каждого риска в ответе `file:line` существует в diff, `evidence` подтверждается строкой diff или правилом репозитория. - Проверка лимита ≤ 3 рисков (OUT-1). - Повторная проверка SCOPE-1 (нет побочных эффектов). | Инкремент 2. CASE.md (QA-1, OUT-1, SCOPE-1). |

- Что исправлено в исходном плане:
  - Убраны учебные артефакты и процессы (например, генерация P1-02) из инкрементов; вместо этого — продуктовые результаты, действия пользователя и проверяемые признаки.
  - В явном виде включены все правила из CASE.md, не только OUT-1/API-1/REL-1, но и QA-1, OBS-1, SCOPE-1, с проверками на каждом шаге.
  - Каждому инкременту даны конкретные критерии наблюдаемого результата и проверки, привязанные к правилам CASE.md.

- Почему новый вариант лучше:
  - Ориентирован на поставку продукта: каждый инкремент даёт полезный и проверяемый результат для конечного пользователя.
  - Риски снижены раньше: API-1 и SEC-1 реализуются до широкого использования LLM; устойчивость (REL-1, OBS-1) закрепляется до улучшений качества.
  - Проверяемость встроена: у каждого шага есть измеримая валидация, соответствующая CASE.md, что упрощает приёмку.

- Что всё ещё требует решения человеком:
  - Итоговое решение по PR всегда принимает человек (SCOPE-1).
  - Настройка и поддержка паттернов редактирования секретов, оценка ложных срабатываний и уточнение источников секретов (риски из ADR).
  - Подбор и операционная настройка модели/провайдера LLM, наблюдение за таймаутами и эксплуатационными метриками.
  - Калибровка правил привязки рисков к diff (QA-1) и оценка полезности списка `checks` на реальных кейсах.

## Что изменили в исходном артефакте

- Файл и раздел: practices/practice_02/rctf/experiment.md — заполнены Role/Context/Task/Format; разделы «Полный запрос», «Что получили», «Что изменили в исходном артефакте».
- Изменение: Уточнён план из трёх инкрементов. Внесены доработки: таймаут/ошибки обрабатывает backend/LLM‑адаптер; «стабильная польза» заменена на DoD (риски подтверждены, ≤3, проверки содержат действие и ожидаемый результат); SEC‑1 учтены разные форматы секретов (токены, пароли, приватные ключи) и риск ложных пропусков, предусмотрена проверка отсутствия секретов в outbound payload. Создан согласованный документ: [project_management.md](project_management.md).
- Как проверили: Соотнесли пункты с CASE.md (API-1, SEC-1, REL-1, OUT-1, SCOPE-1, QA-1, OBS-1). Исходные файлы Practice 1 оставлены без изменений.
- Что отклонили: Учебные шаги (например, P1-02), навязывание конкретных кодов/форматов ошибок вне CASE.md. Субъективные формулировки пользы без проверяемого DoD.
