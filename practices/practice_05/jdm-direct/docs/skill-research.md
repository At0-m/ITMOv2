# Skill research: test-driven-development

## Что делает skill
Помогает не писать код «вслепую»: сначала формализуем ожидаемое поведение тестом. Цикл таков: RED — пишем минимальный тест и убеждаемся, что он падает по ожидаемой причине; GREEN — пишем минимальный код, чтобы пройти тест; REFACTOR — наводим порядок, сохраняя зелёный. Видеть корректно падающий тест важно, иначе мы не доказываем, что тест действительно ловит будущую ошибку. Акцент на observable behavior на границах, а не на деталях реализации — так тесты не мешают рефакторингу и ловят баги, а не «решения».

## Как skill был применён в этом проекте
Feature A:
- тесты были написаны до реализации;
- на RED упали 5 из 7 тестов;
- причина — отсутствующая валидация;
- после реализации стало 7/7 green.

Feature B:
- новые тесты были написаны до реализации;
- на RED упали 4 теста из-за отсутствующей validateAndCalculateAsync;
- существующие 7 тестов Feature A при этом оставались зелёными;
- после реализации весь проект имел 11/11 green.

## Что skill улучшил
- заставил заранее формализовать ожидаемое поведение;
- позволил доказать, что падение связано именно с отсутствующей фичей;
- помог сохранить Feature A при добавлении B.

## Ограничения
TDD доменного слоя сам по себе не гарантировал наблюдаемое поведение в UI. Первый вариант Feature B проходил unit-тесты, но отдельный review показал, что timeout/success/error ещё не были провязаны в UI. После замечания UI был исправлен, и повторный review прошёл успешно.
