Ниже — разбор PR по серьезности. Указываю файлы и места, где это уместно.
Критичные
- app/api.py: отсутствие валидации входа и безопасного доступа к данным. create_review(payload: dict) ожидает payload["diff"]. Если ключа нет или тип не строка, будет KeyError → 500 вместо 422. Нужно Pydantic‑модель запроса и корректные коды ошибок.
- app/api.py, app/review_service.py: использование dict[str, str] в аннотациях. Это работает только с Python ≥ 3.9. Если проект на 3.8, это синтаксическая ошибка на импорт/запуск. Либо переходить на ≥ 3.9, либо заменить на Dict[str, str] из typing или включить from __future__ import annotations и проверить совместимость.
- app/api.py: схема ответа не зафиксирована. Возвращается «произвольный dict» без response_model. Документация OpenAPI получится некорректной, а клиенты — хрупкими.
Серьезные
- app/api.py: нет явной обработки ошибок LLM. Любые исключения из review_service.review приведут к 500. Нужна обработка исключений, маппинг ошибок на 4xx/5xx, таймауты.
- app/review_service.py: отсутствие ограничений/триажа на размер diff. Большие диффы могут превысить лимиты LLM и/или резко увеличить задержки/стоимость. Нужны усечение, чанкинг или отказ с понятной ошибкой.
- app/review_service.py: промптинг уязвим к prompt‑injection. Сырой diff включается без контекстных инструкций и sandboxing. Стоит добавить системные ограничения, формат ответа, и/или пост‑валидацию.
- app/api.py: эндпоинт без аутентификации/авторизации. Если сервис предполагается публичным, это DoS/злоупотребления.
- app/api.py: синхронный обработчик выполняет потенциально долгую сетевую операцию (LLM). В FastAPI sync‑роуты уходят в threadpool, но без таймаутов и контроля пула можно получить истощение воркеров под нагрузкой. Рассмотреть async‑вариант с anyio.to_thread/async llm или ограничители.
Средние
- app/api.py: отсутствие Pydantic‑модели ответа. Сейчас возвращается {"comment": ...} без гарантированной схемы; лучше зафиксировать контракт, возможно со списком проблем, их типами/локациями.
- app/dependencies (косвенно): review_service импортируется как модульная синглтон‑зависимость, минуя механизм зависимостей FastAPI (Depends). Это усложняет тестирование/подмену. Лучше провести через Depends или провайдер.
- app/review_service.py: LLM — Protocol, но нет контракта по поведению (ошибки, таймаут, максимальный размер). Добавьте докстринг/комментарий и инварианты или адаптер.
- Логи/трассировка отсутствуют. Нет аудита входа/ошибок/метрик длительности.
Минорные
- app/review_service.py: мелкая стилистика сигнатуры Protocol: перенос ... на следующую строку не критичен, но исходный вариант был компактнее.
- Язык ответа и промпта — жёстко английский. Если клиенты русскоязычные, стоит унифицировать язык или сделать параметром.
- REST‑деталь: POST на /api/reviews возвращает 200; для создания можно вернуть 201 и Location (если это реально «создание ресурса»). Если это compute‑endpoint — ок.
- Название payload неконкретно; лучше CreateReviewRequest.
Потенциальные несоответствия ожиданиям
- Формат результата слишком минимальный: один ключ comment. Заказчикам обзора PR обычно нужны структурированные находки: список проблем с типами (bug/security/style), ссылками на файлы/строки, severity, кратким описанием и рекомендациями.
Рекомендации по фиксу (кратко)
1. Ввести Pydantic‑модели запроса/ответа и response_model в роуте; валидировать diff, возвращать 422 при ошибках ввода.

3. Добавить обработку ошибок и таймауты LLM; продумать политику усечения/чанкинга diff.

6. Перевести зависимость на Depends для тестируемости; добавить базовые логи и метрики.

## Master Prompt v1

Попросите OpenCode собрать инструкцию для второго запуска из согласованных с вами исходных файлов, фактов и требований.

### 1. Цель и роль

- Цель: провести повторное ревью TRAINING_PR.diff и вернуть результат в формате OUT-1 с учётом Context Pack.
- Роль AI: инженерный AI‑ассистент code review; находит проблемы и предлагает проверки; решение за человеком (SCOPE-1).

### 2. Входы и источники

- Обязательный вход: practices/practice_01/TRAINING_PR.diff.
- Разрешённые файлы и источники: practices/practice_01/README.md, practices/practice_01/context.md.
- Context Pack — факты, правила, примеры и ограничения: см. practices/practice_01/context.md (SEC-1, API-1, REL-1, OUT-1, SCOPE-1, QA-1, OBS-1; хороший/плохой пример).

### 3. Задача и артефакты

- Что сделать: определить, что изменяет PR; найти риски; проверить их по diff и правилам; оставить максимум 3 существенных риска; для каждого дать воспроизводимую проверку.
- Что вернуть: summary, массив risks (до 3) и массив checks согласно OUT-1.

### 4. Формат результата

- Структура ответа: { summary: string, risks: [{file, line, evidence, risk}], checks: [{input/action, expected}] }.
- Ограничения объёма: кратко, без воды; максимум 3 риска.

### 5. Полномочия и запреты

- Разрешено: анализировать diff и источники из раздела 2; давать ссылки file:line и проверки.
- Запрещено: approve/merge, менять код, выдумывать факты без evidence; логировать содержимое diff (OBS-1).

### 6. Рабочий процесс и остановка

- Шаги: 1) Прочитать diff. 2) Сформировать кандидаты в риски. 3) На каждого кандидата: указать evidence из diff и применимое правило. 4) Оставить максимум 3. 5) Для каждого — воспроизводимая проверка. 6) Вернуть в формате OUT-1.
- Когда остановиться и запросить человека: если правило не подтверждается diff/context.md; при неопределённости сообщить «Требуется проверка студентом».

### 7. Проверки и подтверждения

- Как проверять утверждения: claim → evidence → rule → check. Не включать без evidence.
- Какие результаты проверки сохранить: точный фрагмент строки из diff и указание file:line.

### 8. Definition of Done

- Задача закончена, когда: выданы summary, до 3 подтверждённых риска и проверки; структура сохранена; без нарушений SCOPE-1; ссылки на файлы и строки присутствуют.
